## 6. Ponto importante sobre commits e contas do GitHub

Explique claramente como os commits aparecerão no Discord.

O usuário quer entender se, quando houver commits, eles aparecerão separados por conta, autor, repositório, organização ou evento.

Você deve explicar no plano que eventos de commit vindos do GitHub normalmente podem trazer informações como:

* repositório;
* organização ou owner;
* branch;
* autor do commit;
* usuário que realizou o push;
* mensagem do commit;
* hash do commit;
* link do commit;
* lista de arquivos alterados, quando disponível;
* quantidade de commits no push;
* timestamp.

Explique as possibilidades de organização:

### Opção A — Um único canal geral de commits

Todos os commits aparecem em `#github-commits`, mas cada mensagem informa:

```text
Repositório:
Branch:
Autor:
Conta/owner:
Mensagem:
Commit:
Link:
```

### Opção B — Separar por repositório

Criar canais específicos, por exemplo:

```text
#github-app-flutter
#github-site-future-station
#github-backend
```

### Opção C — Separar por tipo de evento

Manter canais assim:

```text
#github-commits
#github-pull-requests
#github-releases
#github-actions
```

### Opção D — Separar por conta/organização

Caso existam commits vindos de GitHub pessoal, GitHub da empresa ou GitHub de colegas, o n8n pode identificar o `repository.owner`, `sender.login` ou `pusher.name` e formatar a mensagem deixando claro de qual conta veio.

Exemplo:

```text
🚀 Novo commit recebido

Origem: GitHub Future Station
Repositório: futurestation/app-flutter
Branch: main
Autor do commit: Igão
Push realizado por: igao-dev
Mensagem: Ajusta componente de login
Commit: abc1234
Link: https://github.com/...
```

### Recomendação esperada

Você deve recomendar a melhor opção para a Future Station neste momento.

A princípio, priorize uma estrutura simples e escalável:

* separar por tipo de evento;
* dentro da mensagem, informar repositório, conta/owner, branch e autor;
* futuramente, se o volume crescer, separar por projeto ou repositório.

## 7. Arquitetura desejada

Considere a arquitetura base:

```text

  ↓

```

## 10. Formato das mensagens automáticas

Proponha modelos de mensagens para o Discord.

### Commit

```text
🚀 Novo commit

Origem: [GitHub pessoal / GitHub Future Station / Organização]
Repositório: [owner/repo]
Branch: [branch]
Autor: [autor do commit]
Push por: [sender/pusher]
Mensagem: [mensagem do commit]
Arquivos alterados: [quantidade, se disponível]
Commit: [hash curto]
Link: [URL]
```

### Pull Request

```text
🔀 Pull Request atualizado

Repositório: [owner/repo]
Título: [título]
Autor: [autor]
Branch: [origem → destino]
Status: [aberto / atualizado / mergeado / fechado]
Link: [URL]
```

### Release

```text
🏷️ Nova release

Repositório: [owner/repo]
Versão: [tag]
Publicado por: [autor]
Resumo: [descrição curta]
Link: [URL]
```

### GitHub Actions

```text
⚙️ GitHub Actions

Repositório: [owner/repo]
Workflow: [nome]
Branch: [branch]
Status: [sucesso / falha / em andamento]
Autor: [sender]
Link: [URL]
```

### Falha crítica

```text
🚨 Falha detectada

Origem: GitHub Actions / Deploy / n8n
Repositório/Workflow: [nome]
Status: [falhou]
Ambiente: [produção / homologação / dev]
Responsável: [quando disponível]
Link: [URL]
```

## 11. Segurança e permissões

Inclua no plano:

### Discord

Verificar necessidade de permissões:

```text
- View Channels
- Send Messages
- Manage Webhooks
- Manage Channels
- Read Message History
- Manage Roles, somente se for mexer em permissões
```

Evitar dar Administrator se não for necessário.

### GitHub

Verificar necessidade de permissões:

```text
- repo, se forem repositórios privados;
- admin:repo_hook para criar webhooks em repositórios;
- read:org, se houver organização;
- admin:org_hook, somente se for usar webhook no nível da organização.
```

Preferir token dedicado com menor privilégio possível.

### n8n

Validar:

```text
- URL pública do webhook;
- credenciais seguras;
- variáveis de ambiente;
- secret do webhook do GitHub;
- workflow desativado até os testes;
- logs de execução;
- tratamento de erro;
- retry/fallback se necessário.
```
