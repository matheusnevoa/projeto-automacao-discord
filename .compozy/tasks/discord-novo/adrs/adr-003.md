# ADR-003: Organize GitHub Notifications by Event Type, not Repository or Owner

## Status

Accepted

## Date

2026-05-27

## Context

GitHub events arriving at the Discord server can be sliced along several axes:

- by event type (push, pull_request, release, workflow_run, ...)
- by repository (one channel per repo)
- by owner / organization (one channel per GitHub account)
- by a single unified channel (everything in one place)

The Future Station team operates a small server (22 members), expects to integrate GitHub repositories incrementally starting with one test repo, and wants every commit to appear as its own message. The team also wants `@dev-alerts` mentions on failures, which requires routing on event type regardless.

## Decision

Notifications are organized into **one channel per GitHub event type** under the `🔗 GITHUB` category:

- `#github-commits` — push events (each commit posts as one message)
- `#github-pull-requests` — pull_request events (opened, updated, reviewed, merged, closed)
- `#github-releases` — release events (published, edited)
- `#github-actions` — workflow_run, deployment_status, and check_run events

Every Discord message embeds repository, branch, author, push actor, owner, and link metadata so that filtering by repo or owner is possible visually inside each channel.

## Alternatives Considered

### Alternative 1: One channel per repository

- **Description**: `#github-app-flutter`, `#github-backend`, `#github-site`, etc. Every event type for a given repo lives in its repo's channel.
- **Pros**: Easy to mute a noisy repo; clear ownership boundary; conversation about a repo concentrates in one place.
- **Cons**: Number of channels grows linearly with repos; mixes commits with high-volume PR comments and Actions runs; defeats the goal of routing failures to a specific channel with `@dev-alerts`.
- **Why rejected**: Doesn't scale gracefully and breaks the failure-routing requirement.

### Alternative 2: One channel per owner / organization

- **Description**: Separate channels for `#github-futurestation-org`, `#github-personal`, `#github-clients`.
- **Pros**: Useful if multiple distinct GitHub accounts are mixed; clear privacy boundary.
- **Cons**: Future Station today operates as a single business context — the owner dimension is low-value. Same problem with mixing event types within each channel.
- **Why rejected**: Doesn't match the current account topology and provides no benefit.

### Alternative 3: Single `#github` channel

- **Description**: All events in one channel, formatted clearly.
- **Pros**: Simplest possible setup; everything visible in one stream.
- **Cons**: Becomes noisy as soon as multiple repos are added; impossible to mute one event type without muting all; failure events get buried.
- **Why rejected**: Doesn't scale beyond the first repository.

## Consequences

### Positive

- Channel count grows with event types (bounded ~5) rather than with repositories (unbounded).
- `@dev-alerts` mentions can target the specific failure channel cleanly.
- Team members can mute event types they don't care about (e.g., mute `#github-actions` if not on-call).
- Each channel's purpose is self-evident from its name.

### Negative

- Conversation about a specific repo is split across four channels.
- Filtering "show me everything that happened in repo X today" requires scrolling through multiple channels (or using Discord search).

### Risks

- **Risk**: If one repository becomes much noisier than others, it floods every event channel.
  - **Mitigation**: n8n workflow can add per-repo filters or rate limits; Phase 4 of the plan covers digest/summary patterns.
- **Risk**: Adding new GitHub event types in the future may require new channels.
  - **Mitigation**: Acceptable — adding a channel is cheap and predictable.

## Implementation Notes

- Every embed includes a header line of the form `repo · branch · author` so that visual scanning per repo is possible inside an event channel.
- `#github-teste` is a separate test channel used only during Phase 1 validation; it does not represent a long-term event-type channel and may be deleted after Phase 2.
