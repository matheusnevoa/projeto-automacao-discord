# ADR-005: GitHub Webhook HMAC-SHA256 Verification in Phase 1

## Status

Accepted

## Date

2026-05-27

## Context

GitHub webhooks support an optional shared secret. When set, GitHub signs every delivery with HMAC-SHA256 over the raw body and sends the digest in the `x-hub-signature-256` header. The receiver verifies the digest before trusting the payload.

The n8n Webhook Trigger URL has a path-embedded token by default, but that token is the only line of defense if secret verification is off. Anyone who learns the URL (logs, screenshots, accidental commit) can POST forged GitHub-shaped payloads.

The PRD originally flagged this as an Open Question — defer to Phase 2 or implement from day one. The user chose Phase 1.

## Decision

Phase 1 of `WF-GH-Discord` includes HMAC-SHA256 verification as the first node after the Webhook Trigger.

Verification logic (in a `Code - Verify HMAC` node):

1. Read raw body from `$input.first().json.body` or `$('Webhook').first().json.body` depending on n8n version.
2. Read signature from header `x-hub-signature-256` (format: `sha256=<hex>`).
3. Compute HMAC-SHA256 of the raw body using `$vars.GITHUB_WEBHOOK_SECRET` as the key.
4. Compare digests using a constant-time comparison (manually implemented if `crypto.timingSafeEqual` is not available in the Code node's Node.js runtime; otherwise use it).
5. If the digests do not match, throw a controlled error tagged `HMAC_INVALID` so `WF-ERR Global` records the rejection in `#erros-producao` (or, in Phase 2, in `#n8n-logs` as a warning if the volume of probes is high).
6. If the digests match, pass the parsed payload downstream.

Every GitHub repository connected to the n8n endpoint must be configured with the same secret value.

## Alternatives Considered

### Alternative 1: Defer to Phase 2

- **Description**: Configure the secret in GitHub immediately but do not validate inside the workflow until the message format is locked.
- **Pros**: Saves the ~30 minutes of building the verification node during the Phase 1 push.
- **Cons**: A leaked Webhook Trigger URL during testing would let anyone inject forged events into the Discord channels.
- **Why rejected**: Cost is small, exposure is real, the user explicitly chose Phase 1 enforcement.

### Alternative 2: Skip the secret entirely

- **Description**: Rely only on the n8n Webhook Trigger URL's path token.
- **Pros**: Zero workflow code.
- **Cons**: Single point of failure for authentication; the URL appears in GitHub UI under "Recent Deliveries" and could be screenshotted or leaked.
- **Why rejected**: The PRD's security stance treats webhook URLs as secrets; relying solely on the path token contradicts that posture.

## Consequences

### Positive

- Forged payloads cannot reach the formatter or the Discord channels.
- Secret rotation is a one-variable change in `$vars.GITHUB_WEBHOOK_SECRET` plus updating the GitHub repository settings.
- The verification node is reusable for any future GitHub-fed workflow.

### Negative

- One additional node (Code) in every execution; negligible runtime cost.
- A rotation requires coordinating change in n8n and in every connected GitHub repository at the same time.

### Risks

- **Risk**: Secret value is stored as plaintext inside n8n Variables; an n8n admin can read it.
  - **Mitigation**: n8n admin access is already the trust boundary for this whole pipeline. Treat the secret like any other credential in the instance.
- **Risk**: Timing-safe comparison implementation in the Code node may not behave identically across n8n versions.
  - **Mitigation**: Use `crypto.timingSafeEqual` on Buffers when available; fall back to a manual byte-by-byte comparison that does not short-circuit.

## Implementation Notes

- Node name: `Code - Verify HMAC`.
- Position: directly after the `Webhook` trigger node, before the `Switch` on `x-github-event`.
- On failure: `throw new Error('HMAC_INVALID')` so the n8n Error Workflow setting routes it to `WF-ERR Global`.
- Secret name in `$vars`: `GITHUB_WEBHOOK_SECRET`.

Reference snippet (illustrative, not normative):

```javascript
const crypto = require('crypto');
const body = $input.first().binary?.data ?? JSON.stringify($input.first().json);
const sigHeader = $input.first().json.headers['x-hub-signature-256'] || '';
const expected = 'sha256=' + crypto
  .createHmac('sha256', $vars.GITHUB_WEBHOOK_SECRET)
  .update(body)
  .digest('hex');
if (sigHeader.length !== expected.length ||
    !crypto.timingSafeEqual(Buffer.from(sigHeader), Buffer.from(expected))) {
  throw new Error('HMAC_INVALID');
}
return $input.all();
```
