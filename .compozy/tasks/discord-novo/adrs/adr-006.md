# ADR-006: One Code Node per Event Type for Formatting

## Status

Accepted

## Date

2026-05-27

## Context

The pipeline transforms GitHub events into Discord messages. Each event type has its own embed shape, color, set of fields, and rules for when to inject the `@dev-alerts` role mention. The `push` event additionally needs to produce one Discord message per commit in the `commits[]` array, not one message per push.

Three placement strategies were viable inside `WF-GH-Discord`:

- A single Code node before the Switch that builds the entire `{ content, embeds, targetChannelUrl }` for any event type.
- A Code node per branch of the Switch — one per event type.
- A Set node per branch of the Switch — declarative, no JavaScript.

The existing `WF1` workflow uses Code nodes named `Code - <Purpose>` (e.g., `Code - Selecao melhor match`) and Set nodes named `Set - <Purpose>`, and applies them per branch of an If/Switch.

## Decision

`WF-GH-Discord` will have **one Code node per event type** after the Switch:

- `Code - Format Push` — splits `commits[]` and emits one item per commit.
- `Code - Format PR` — formats one pull_request action.
- `Code - Format Release` — formats one release event.
- `Code - Format Action` — formats one workflow_run / deployment_status, injecting `<@&dev-alerts>` if conclusion=failure or state=failure.

Each Code node sets the JSON payload (Discord `content` + `embeds`) and a target channel webhook URL pulled from `$vars`. The downstream HTTP Request node executes one POST per item.

## Alternatives Considered

### Alternative 1: Single Code node before the Switch

- **Description**: One Code node receives the event, builds the full payload (including which channel URL to target), and the Switch only routes the HTTP Request to the right Discord channel (or all routes converge to the same HTTP Request reading the URL from the item).
- **Pros**: All formatting in one file; easy to read end-to-end without jumping between branches.
- **Cons**: The single Code grows quickly as event types and edge cases multiply; testing one event type in isolation requires running the whole node; the file becomes the bottleneck for any change.
- **Why rejected**: Worse modularity than per-event Codes; harder to read once it crosses ~100 lines.

### Alternative 2: Set node per branch

- **Description**: Each Switch branch ends in a Set node that builds the payload via n8n expressions.
- **Pros**: Declarative; no JavaScript; visible in the UI without opening a Code editor.
- **Cons**: `push` events with multiple commits need item-array transformation, which is awkward in Set; logic for "is this a failure?" must be expressed as nested ternaries.
- **Why rejected**: Set is good for flat payload shaping but not for array-fanout and conditional mention injection.

## Consequences

### Positive

- Each event type is testable in isolation by pinning input data on its Code node.
- A failure in formatting `push` (the noisiest event) cannot break `release` or `workflow_run`.
- New event types are added by extending the Switch and adding one more `Code - Format <Event>` node — no edits to existing branches.
- Naming aligns with `WF1` (`Code - Selecao melhor match`).

### Negative

- Four Code nodes to maintain instead of one.
- Common helpers (e.g., short-SHA formatter, emoji palette) must be duplicated or factored into a small shared library inside each Code (JS does not natively support n8n-side imports).

### Risks

- **Risk**: Duplicated helpers drift between Code nodes.
  - **Mitigation**: Keep helpers minimal (3–5 lines each); document the canonical form in a `// HELPERS` block at the top of each Code; if drift becomes painful, factor into a single `Code - Format Common` node placed before the Switch.

## Implementation Notes

- Each Code node returns an array. Single-item events (`pull_request`, `release`, `workflow_run`) return a 1-element array. `push` returns `commits.length` items.
- Each item carries the resolved `targetChannelUrl` so the downstream HTTP Request reads it from `{{$json.targetChannelUrl}}`.
- The `Code - Format Action` node is the only one that decides `<@&dev-alerts>` is needed; the others never inject role mentions.
