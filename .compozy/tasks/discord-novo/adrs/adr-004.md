# ADR-004: HTTP Request to Discord Channel Webhook (not n8n Discord node)

## Status

Accepted

## Date

2026-05-27

## Context

`WF-GH-Discord` posts messages to several Discord channels (`#github-commits`, `#github-pull-requests`, `#github-releases`, `#github-actions`, `#github-teste`, `#n8n-logs`, `#deploys`, `#erros-producao`). Each message must support:

- Rich embeds (color per event type, title, fields, link).
- Mentions of the `@dev-alerts` role inside the `content` field on failure events.
- Different Discord channel webhook URL per branch of the Switch.

n8n offers three viable sender mechanisms:

- Generic HTTP Request node POSTing JSON to a Discord channel webhook URL.
- Native Discord node configured with a Discord Bot credential (Send Message operation).
- Native Discord node configured with a Discord Webhook credential.

The workflow also already follows a convention seen in `WF1`: outbound API calls use `HTTP Request` nodes named `HTTP Request - <Purpose>`.

## Decision

`WF-GH-Discord` will use **HTTP Request nodes** to POST JSON payloads directly to each Discord channel webhook URL.

Payload shape:

```json
{
  "username": "Future Station GitHub",
  "content": "<@&{{$vars.DEV_ALERTS_ROLE_ID}}> 🚨 ...",
  "embeds": [{ "title": "...", "color": 0xFF0000, "fields": [...], "url": "..." }]
}
```

Channel webhook URLs are read from `$vars.DISCORD_WH_*` (see ADR-005). Naming follows `HTTP Request - Send to <channel>` (consistent with `WF1`).

## Alternatives Considered

### Alternative 1: Native Discord node with Bot credential

- **Description**: Configure a Discord Bot, store the bot token as a Discord Bot credential, and use the Discord node's "Send Message" operation with channel ID.
- **Pros**: Credentials managed by n8n; richer interactions available (reactions, threads, member operations) if needed later.
- **Cons**: Requires the bot to be in the server and have channel-level Send Messages permission for every target channel; bot token has wider scope than a per-channel webhook; the node's Send Message operation has known limitations posting embeds combined with role mentions in `content` across n8n versions.
- **Why rejected**: Webhook URLs are scoped per channel (least privilege); embed + role-mention combination via HTTP Request is well-documented and stable; no need for the broader bot capabilities in MVP.

### Alternative 2: Native Discord node with Webhook credential

- **Description**: Use the Discord node configured with the "Discord Webhook" credential type, which wraps the same webhook URL.
- **Pros**: Less raw JSON in the workflow; native field mapping in the UI.
- **Cons**: Adds a credential per channel (8 credentials), each with one URL; rotating a single URL still requires opening that credential; less obvious how the role mention is injected into `content`; not aligned with the existing `HTTP Request - <Purpose>` convention.
- **Why rejected**: Operational overhead is higher than `$vars` + HTTP Request without delivering a meaningful improvement.

## Consequences

### Positive

- Single, uniform pattern for every event type — HTTP Request + JSON body.
- Per-channel URLs stored in `$vars` (ADR-005) — rotation is one variable edit, no credential edits.
- Discord embeds and role mentions behave deterministically; format documented in Discord's webhook API.
- Aligns with `WF1` naming convention.

### Negative

- The team manually maintains the JSON shape; a typo in a payload key only surfaces at runtime as a Discord 400.
- No native UI hint for Discord-specific fields; reviewers must know the embed schema.

### Risks

- **Risk**: Discord deprecates or changes the webhook payload contract.
  - **Mitigation**: Discord versioning has been stable; if changes happen, only the Code formatter nodes need updating.
- **Risk**: A bad payload silently fails (returns 400) without the user noticing.
  - **Mitigation**: HTTP Request node's "Continue On Fail" is off by default — failures throw and route to `WF-ERR Global`, which surfaces them in `#erros-producao`.

## Implementation Notes

- HTTP method: `POST`.
- Content-Type: `application/json`.
- Authentication: none on the request (the URL token is the auth).
- Headers: only `Content-Type`.
- Body: JSON from the previous Code node (`{ "content": ..., "embeds": [...] }`).
