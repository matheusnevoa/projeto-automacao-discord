# ADR-001: n8n as Central Hub for GitHub → Discord Pipeline

## Status

Accepted

## Date

2026-05-27

## Context

The Future Station team needs automated notifications from GitHub repositories into the Discord server (commits, pull requests, releases, GitHub Actions). The team already operates an n8n instance at `n8n.futurestation.com.br` with 26 existing workflows including a centralized error handler (`WF-ERR - Error Handler Global`) and a numbered workflow pattern (`WF1`–`WF5`).

Three architectural options were available:

- Route all events through a single n8n workflow that branches by event type.
- Wire GitHub webhooks directly to Discord using the native `/github` webhook endpoint (no n8n).
- Split routing into multiple n8n workflows, one per event type, behind a dispatcher.

Constraints shaping the decision:

- Failure notifications must mention a dedicated `@dev-alerts` Discord role (decided in brainstorming).
- Each commit must appear as one distinct Discord message (decided in brainstorming).
- The pipeline must allow filtering by branch, author, repository, and event subtype.
- The MVP scope is intentionally minimal (only two new Discord categories), so operational overhead must stay low.
- The team already trusts n8n as the automation backbone, and the existing `WF-ERR Global` pattern can absorb pipeline failures.

## Decision

The pipeline will use **a single centralized n8n workflow** (`WF-GH-Discord`) as the only intermediary between GitHub and Discord.

GitHub webhooks point to one n8n Webhook Trigger URL. The workflow inspects the event type, applies filters (repository, branch, author), formats a Discord-friendly embed, and posts to the appropriate Discord channel webhook. Failure events route through formatting that injects an `@dev-alerts` mention. Errors inside the workflow are captured by the existing `WF-ERR Global` handler.

## Alternatives Considered

### Alternative 1: Native Discord `/github` webhook (no n8n)

- **Description**: Configure each GitHub repository to post directly to a Discord webhook URL appended with `/github`. Discord renders the GitHub payload natively.
- **Pros**: Zero workflow maintenance, two-minute setup per repository, no dependency on n8n uptime.
- **Cons**: Native GitHub embed format is verbose and not customizable; cannot inject role mentions on failure events; cannot filter by branch, author, or event subtype; would require one Discord webhook per channel × per event type, multiplying configuration.
- **Why rejected**: Directly contradicts the requirement to mention `@dev-alerts` on critical failures and removes all flexibility needed for the future evolution phases described in the original plan.

### Alternative 2: Modular — one n8n workflow per event type

- **Description**: A thin dispatcher workflow forwards each event to one of four specialized workflows (`WF-GH-Commits`, `WF-GH-PRs`, `WF-GH-Releases`, `WF-GH-Actions`), each handling its own formatting and delivery.
- **Pros**: Isolation per event type, smaller workflows that are easier to reason about, closer match to the existing `WF1`/`WF2`/`WF3`/`WF4`/`WF5` modular pattern.
- **Cons**: Five workflows to create, monitor, and maintain instead of one; higher operational overhead for the explicitly-requested minimal MVP; harder initial debugging because state flows across workflows.
- **Why rejected**: Overkill for the minimal MVP scope (one test repository, low expected volume). The chosen design can be refactored to this pattern later as a non-destructive migration if volume justifies it.

## Consequences

### Positive

- Single source of truth for the entire GitHub → Discord pipeline.
- Full control over message formatting, filters, and conditional routing.
- Role mentions, branch/author filters, and per-event embed styles can be added incrementally inside one workflow.
- Aligns with the existing `WF-` naming and `WF-ERR Global` error-handling convention already in the n8n instance.
- Refactoring to a modular design later is incremental, not destructive.

### Negative

- One workflow concentrates all routing logic; readability degrades as event types and filters grow.
- A bug in the central workflow affects every event type simultaneously until rolled back.

### Risks

- **Risk**: n8n instance downtime causes lost GitHub events.
  - **Mitigation**: GitHub retries webhook deliveries on failure; rely on `WF-ERR Global` for in-workflow exceptions; monitor `#n8n-logs` and `#erros-producao` for delivery failures.
- **Risk**: Discord webhook rate limits when many commits land in a short window.
  - **Mitigation**: Phase 1 ships per-event delivery; if rate limits trigger, add a queue/batcher inside the same workflow without changing the architecture.

## Implementation Notes

- Workflow name: `WF-GH-Discord` to match the existing `WF-*` convention.
- Webhook Trigger URL is the single endpoint registered in GitHub.
- A Switch node routes by `headers["x-github-event"]`.
- Each branch ends in an HTTP Request node pointing to the matching Discord channel webhook.
- Failure paths (`workflow_run` with `conclusion=failure`, `deployment_status` with `state=failure`) inject `<@&dev-alerts-role-id>` into the message content.
